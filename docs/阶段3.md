# 阶段3：自研分布式流量控制组件

## 目标

手写三个流量治理组件——分布式令牌桶限流、熔断状态机、热点探测自动降级——而不是接入 Sentinel 这类现成方案，用真实故障场景（停掉 MySQL、并发打热点商品）验证每一个都确实生效。这三个组件都放在独立的 `com.pulserank.governance` 包下，不依赖业务代码，理论上可以整体搬到别的 Spring Boot 项目里复用，这是"可插拔组件"的核心含义——一个能拆出来单独用的内聚模块，不一定非要拆成单独的 Maven 制品才算数。

## 做了什么

**分布式令牌桶限流**（`TokenBucketRateLimiter` + `RateLimitInterceptor`）：桶的状态（剩余令牌数、上次补充时间）存在 Redis 一个 Hash 里，"读取剩余令牌 → 按时间差补充 → 扣减 → 写回"这套逻辑写成一段 Lua 脚本，通过 Redisson 的 `RScript` 原子执行。多个应用实例共享同一个 Redis key，限的是整个集群的总流量，不是每个实例各算各的。挂在 `GET /api/products/*/score` 这个查询接口上，超限返回 `429`。

**熔断状态机**（`CircuitBreaker`）：CLOSED → OPEN → HALF_OPEN 三态，保护的是"直接查数据库"这条路径。连续失败达到阈值（默认5次）跳闸进 OPEN，冷却期（默认5秒）内所有请求直接快速失败，不再尝试连库；冷却期结束后放几个探测请求进 HALF_OPEN，成功就关闭回到 CLOSED，失败就重新跳闸。熔断打开时返回一个 `source: "DEGRADED"` 的降级响应，不写入缓存。

**热点探测自动降级**（`HotKeyDetector` + `HotKeyAwareExpiry`）：给每个 `productId` 维护一个 1 秒滑动窗口的访问计数，超过阈值（默认20次/秒）就标记为热点，标记持续 10 秒。阶段1 的 L1 本地缓存（Caffeine）原本是统一 5 秒 TTL，现在换成自定义的 `Expiry` 实现：普通 key 还是 5 秒，被标记热点的 key 给 30 秒——用更长的本地缓存时间换取对 Redis/数据库更少的回源次数。

## 为什么这样做

**限流为什么要"分布式"，而不是每个实例自己控制**：如果每个实例各自维护一个本地令牌桶，集群扩容到 N 个实例时，总的放行流量会变成单实例配置的 N 倍——这跟"给后端设一个总的流量上限保护它"这个限流的初衷是矛盾的。把桶状态放到 Redis 里让所有实例共享同一份预算，才是"分布式流量控制"这个说法真正要解决的问题，也是 JD 里这个词具体指向的能力。

**为什么用 Lua 脚本而不是"读一下 Redis、算一算、再写回去"这种分步操作**：分步操作在并发场景下有竞态——两个请求同时读到"还剩3个令牌"，都以为自己能拿到令牌，就会超发。Lua 脚本在 Redis 服务端单线程执行，保证整个"读-算-写"是一个不可分割的原子操作，这是实现分布式限流必须解决的正确性问题，不是可选项。

**熔断器为什么要包一层"是否允许请求"的判断，而不是等数据库调用超时了再处理**：如果每次都真的去发起数据库连接、等它超时才判定失败，故障期间每个请求依然要付出一次完整的超时等待代价，用户体验和系统吞吐都没有改善。只有在 OPEN 状态下完全跳过数据库调用、直接返回降级结果，才能做到"快速失败"，这也是"熔断"这个词字面意义所在。

**踩坑：熔断器要真正做到快速失败，数据库连接超时本身也得调短**。一开始用 HikariCP 默认的 30 秒 `connection-timeout` 测试，前 5 次失败请求每次都要真等 30 秒才判定失败，熔断跳闸前的这几次请求跟没有熔断器时一样慢——熔断器只能保证"跳闸之后"快，跳闸之前判定失败的速度取决于被保护操作本身的超时设置。把 `spring.datasource.hikari.connection-timeout` 从默认 30000ms 调到 2000ms 后，5 次失败总共只花 10 秒左右就能跳闸，这本身也是更合理的生产配置——没有理由让一次数据库连接尝试拖到 30 秒。

**热点探测为什么不是简单地把所有 key 的 TTL 都调长**：本地缓存 TTL 越长，数据不一致的时间窗口越大（评分更新后，读到旧值的时间更久）。给所有 key 统一调长 TTL 是拿全局的一致性换全局的性能，而热点探测是只给"确实在被高频访问"的那一小撮 key 特殊对待——多数商品不受影响，只有真正扛不住的热点才延长缓存时间，性价比更高。

## 验证方式

**限流**：对一个已预热的商品连续发 100 个请求（容量50、每秒补充20），实际观察到 81 个 `200`、19 个 `429`，和配置的桶容量+补充速率数量级吻合。

**熔断**（真实停 MySQL 容器，不是模拟异常）：

```
docker stop pulserank-mysql
第1-4次请求：每次耗时约2.0s，DEGRADED（连接超时，circuitState=CLOSED，失败计数递增）
第5次请求：耗时约2.0s，DEGRADED（第5次失败触发跳闸，circuitState=OPEN）
第6-8次请求：每次耗时约0.01s，DEGRADED（熔断已打开，直接跳过数据库，日志打印CIRCUIT_OPEN）

docker start pulserank-mysql（等健康检查通过，超过5秒冷却期）
再次请求：source=DB，正常查库成功（HALF_OPEN探测成功，自动转回CLOSED）
之后请求：source=L2 → L1，缓存链路完全恢复正常
```

日志里 `circuitState` 字段清楚地记录了 CLOSED→OPEN 的跳闸时刻和之后每次请求都被正确拦截，全程没有人工介入。

**热点探测**：对一个商品并发打 25 个请求（阈值20次/秒），日志打印 `HOT_KEY_DETECTED`。之后单独验证 L1 缓存存活时间：

```
普通(非热点)商品：7秒后请求 → source=L2   (5秒TTL已过期，正常回落)
热点商品：        7秒后请求 → source=L1   (30秒TTL还没到，仍然命中本地缓存)
```

两组对照清楚地证明了热点 key 拿到了更长的本地缓存时间，普通 key 行为跟阶段1完全一致没有被误伤。
