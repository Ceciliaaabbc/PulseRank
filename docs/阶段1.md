# 阶段1：多级缓存 + 分布式锁防击穿 + 分库分表

## 目标

在阶段0"实时查库"的基线之上，引入 L1(Caffeine)+L2(Redis) 多级缓存、Redisson 分布式锁防缓存击穿、按 `product_id` 分表，用真实压测数据证明这些手段确实提升了读路径的吞吐和延迟表现，而不是只把中间件接上就算完成。

## 做了什么

**多级缓存读路径**（`ScoreQueryService`）：`GET /api/products/{id}/score` 先查 L1 本地缓存（Caffeine，TTL 5s）→ 未命中查 L2 Redis（Redisson `RBucket`，TTL 60s）→ 都未命中才查数据库。响应里加了一个 `source` 字段（`L1`/`L2`/`DB`/`DB-fallback`），标出这次请求实际是被哪一层缓存挡住的，方便验证多级缓存是否真的生效，不是生产 API 该有的字段，纯粹为了本阶段可观测。

**Redisson 分布式锁防缓存击穿**：L1、L2 都未命中时，不是直接放行查库，而是先抢一把以 `product_id` 为粒度的 Redisson 锁——同一个热点商品缓存失效的瞬间，只放一个请求真正查库重建缓存，其他并发请求要么等锁持有者填好缓存后直接读 L2，要么等待超时后降级直接查库（避免锁等待无限阻塞影响可用性）。

**评分写入后失效缓存**：`POST /api/ratings` 落库成功后主动清掉该 `product_id` 的 L1 和 L2 缓存，下一次读会重新查库拿到最新聚合值，不是等 TTL 自然过期。

**分表**：按 `product_id % 4` 把 `rating` 表拆成 `rating_0`～`rating_3` 四张物理表，写入和聚合查询都先算出分片再路由到对应物理表。因为分片键就是查询条件本身，单次查询永远只命中一张表，不需要跨分片合并结果。

## 为什么这样做

**L1 TTL(5s) 远小于 L2 TTL(60s)**：本地缓存允许短暂不一致，但这个窗口要压得足够小；Redis 作为共享的第二层兜底，可以给更长的 TTL 减少回源数据库的频率。两层给不同 TTL 是有意的分层设计，不是随便取的数字。

**为什么要专门加分布式锁防击穿，而不是直接缓存失效后各自查库**：如果不加锁，一个高频访问的商品评分缓存一过期，成百上千个并发请求会同时穿透到数据库，可能瞬间打满数据库连接池——这正是"高并发服务稳定性"要防的典型场景之一。用锁把"重建缓存"这件事收敛成只有一个线程做，是业界标准做法。

**写入后主动失效而不是等 TTL 过期**：评分数据変更后如果只靠 TTL 自然过期，最坏情况下用户会看到长达 60 秒的过期聚合值；主动失效能把这个不一致窗口压缩到几乎为零，代价只是多一次 Redis/本地缓存的删除操作，性价比很高。

**分片键选 `product_id`**：因为所有查询都是"按某个商品查询其聚合评分"，用 `product_id` 分片能保证单次查询永远落在一张物理表内，不需要 ShardingSphere 之类中间件常见的"跨分片归并"逻辑（那是分片键和查询条件不一致时才需要解决的问题）。

**没有用 ShardingSphere，手写了分表路由**：原计划用 ShardingSphere-JDBC 接入分库分表。实际接入时遇到一个真实的、目前在 Maven Central 上无解的版本冲突：ShardingSphere 5.4.1（该组件在 Central 上的最新可用版本）内部持久化元数据时用到的 `ShardingSphereYamlRepresenter` 依赖 snakeyaml 已经移除的无参构造方法 `Representer()`；而 Spring Boot 3.5.7 要求的 snakeyaml 版本（2.4）又必须有 `TagInspector` 类（2.0 才引入，同时移除了那个无参构造方法）——两边的版本要求互斥，没有一个 snakeyaml 版本能同时满足。往下查发现 ShardingSphere 这个版本本该用来避开该问题的 "Memory" 模式也已经被移除，没有绕过办法。与其困在一个第三方组件当前无解的 bug 上，不如把同样的分片路由逻辑（按分片键取模、路由到对应物理表、单分片查询）在应用层用 `JdbcTemplate` 手写出来——核心的分片思路完全一致，也确实跑通了。代价是从 Spring Data JPA 换成了 `JdbcTemplate`（阶段0 用的 Hibernate/JPA 单表映射，在运行时按分片键动态换表这件事上帮不上忙，索性一起换掉，避免应用里同时存在两套数据访问方式）。

## 验证方式

**多级缓存分层命中**：连续请求同一 `product_id`，观察响应里的 `source` 依次变化：

```
POST 两条评分 → GET → source=DB      (冷启动，无缓存)
GET (立即再查)  → source=L1          (本地缓存命中)
sleep 6s (L1 5s TTL 过期，L2 60s 未过期)
GET             → source=L2          (回落到 Redis 命中)
POST 新评分（触发失效）→ GET → source=DB   (重新查库，均值也确实变了)
```

全部符合预期。

**缓存击穿防护**：先用一次写入使某商品缓存失效，紧接着用 `ab -n 50 -c 50` 对同一个 URL 发 50 个并发请求，统计应用日志里 `DB_QUERY productId=2001` 出现的次数——防护生效前应该是 1（只有锁的持有者真正查了库），实测确实是 1，其余 49 个请求都被锁等待或缓存回填挡住了，没有穿透到数据库。

**分表路由正确性**：分别提交 `productId = 1,2,3,4,5` 的评分，直接查 MySQL 确认落表位置：`product_id % 4` 为 0/1/2/3 分别落进 `rating_0`/`rating_1`/`rating_2`/`rating_3`，其中 1 和 5 同落在 `rating_1` 但各自的聚合查询互不影响（`WHERE product_id = ?` 天然隔离）。

**性能对比（无缓存 vs 多级缓存）**：用 `git worktree` 把阶段0 的代码单独跑一份在 8082 端口（真实的"无缓存"服务，不是模拟），阶段1 代码跑在 8081（缓存预热后），用 `ab` 对同一个热点商品做背靠背压测，`c=100 n=2000`：

| | QPS | P50 | P90 | P99 |
|---|---|---|---|---|
| 阶段0（无缓存，每次查库） | 1345 | 40ms | 105ms | 190ms |
| 阶段1（多级缓存命中） | 5693 | 16ms | 26ms | 41ms |
| 提升 | **4.2x** | **60%↓** | **75%↓** | **78%↓** |
