# 阶段5：全链路压测 + 混沌工程

## 目标

把前面几个阶段搭的稳定性机制（多级缓存、分布式锁、Kafka 削峰、限流、熔断、热点探测）放到一起，用两类实验检验它们是不是真的在协同工作而不是各自为战：一是模拟大促级别的读写混合流量冲击，二是故意制造真实故障（真的停容器，不是模拟异常）看系统会不会崩、崩了能不能自己恢复。这一阶段的价值不在于"证明系统没问题"，而在于**主动找问题**——找到的问题该修就修，不为了让报告好看而回避。

## 做了什么

**全链路压测**：同时对读接口（`GET /score`，c=50）和写接口（`POST /ratings`，c=10）各打 30 秒持续流量，模拟大促场景下"看的人远比评分的人多"的真实流量形状，而不是只压测单一接口。

**三个混沌实验**：真实用 `docker stop`/`docker start` 制造故障，不是在代码里模拟异常抛出：
1. 停 Redis，观察限流、多级缓存、分布式锁这些强依赖 Redis 的组件表现
2. 停 MySQL，在真实并发下（不是阶段3那种单请求依次测）观察熔断器表现
3. 停 Kafka，观察写路径的实际行为

## 混沌实验发现的问题（这是本阶段最重要的产出）

**问题1：Redis 故障会直接打挂整个读接口（已修复）**。真的停掉 Redis 容器后请求一个未缓存商品，返回的是 `HTTP 500`，不是预期中"至少能查库兜底"。查日志发现根因是 `RateLimitInterceptor`——限流拦截器在请求进 Controller 之前就要执行一次 Redis Lua 脚本，这个调用没有做异常处理，Redis 不可用时异常直接冒泡成 500。**限流器本来是用来保护后端的辅助机制，结果自己的依赖故障变成了新的单点故障**，这个本末倒置必须修。

**修复方式**：`RateLimitInterceptor` 捕获限流调用的异常，改成 **fail-open**（放行）而不是 fail-closed（拒绝）——限流依赖不可用时宁可暂时不限流，也不能因为限流本身故障而拒绝所有正常请求。同时把 `ScoreQueryService` 里所有直接调用 Redis 的地方（L2 读、L2 写、分布式锁）都包一层 try/catch，失败就跳过对应环节退化到"直接查库"，而不是让异常继续往外抛。

**问题2：Redis 故障会导致 Kafka 消费的评分被重复插入（已修复，这个比问题1更严重）**。`RatingEventConsumer` 处理一条消息的顺序是"先插库、再调用 `evict()` 失效缓存"。`evict()` 内部调用 Redis 删除缓存 key，Redis 挂了之后这行代码抛出异常，异常从 `@KafkaListener` 方法里抛出去，触发 Spring Kafka 默认的重试机制——**但重试重新执行的是整个监听方法，insert 那一步也被重新执行了一遍**。实测：Redis 断线期间提交一条评分，几秒之内这条记录在数据库里从 1 行变成了 5 行、6 行，还在继续涨。这不是"体验降级"，是**实打实的数据被写错**，比问题1严重得多。

**修复方式**：`evict()` 内部捕获 Redis 异常，只记一条警告日志，绝不向外抛出。落库这一步本身是成功的，缓存失效失败的代价顶多是这个商品的聚合值在 Redis TTL 内多返回几次旧数据，比"同一条评分被写库五六次"这种数据污染轻得多。这条踩坑记录也印证了一个更通用的原则：**Kafka 消费者方法里，只要某个操作失败后会触发整条消息重试，就必须想清楚"重试会不会把已经成功的副作用再做一遍"**，不是所有异常都应该老老实实往外抛。

## 混沌实验验证通过、不需要修的部分

**Kafka 短暂故障期间写路径完全不受影响**：停 Kafka 后提交评分，`POST /api/ratings` 依然在 3ms 内返回 202——`KafkaTemplate.send()` 本身是异步的，只是把消息交给生产者客户端内部的缓冲区和重试逻辑，不会阻塞调用方等待 broker 确认。Kafka 恢复后，之前那条消息在客户端默认的 `delivery.timeout.ms`（120秒）重试窗口内被自动送达、正常消费，没有额外代码就自然具备了这个韧性。这里有一个诚实要指出的边界：如果故障时间超过这个重试窗口，消息会真的丢失，而调用方在这之前已经拿到了 202——这是"异步削峰"本身的设计代价（响应不再和真正落库绑定），不是这次没修的 bug，是这个模式一开始就要接受的权衡。

**修复后重新验证 Redis 故障场景**：同样的操作（停 Redis、请求未缓存商品、提交评分）——GET 请求正常返回 `200`（`source: DB`，日志里能看到限流放行和缓存降级的警告，但不再是 500）；POST 之后消费者正确处理，数据库里精确只有 1 行，没有重复。

**MySQL 故障下的熔断器在真实并发下依然工作正常**：停 MySQL 后用 20 个并发请求同时打同一个未缓存商品，全部在几秒内返回 `200`（带 `DEGRADED` 标记），没有一个请求挂起等待数据库连接超时——阶段3 验证的是单请求依次测试，这次是真实并发下的复测，结论一致。

读写并发混合流量，各打满 30 秒：

| 接口 | QPS | P50 | P90 | P99 | 说明 |
|---|---|---|---|---|---|
| `GET /score`（c=50） | 8919 | 5ms | 7ms | 18ms | 267557 个请求里 266667 个被限流拦截返回 429，符合预期——限流阈值(容量50+每秒补充20)本来就是按"保护后端"设的，不是按"扛住这个压测规模"设的 |
| `POST /ratings`（c=10） | 3523 | 2ms | 4ms | 8ms | 105705 个请求全部 202，Kafka 消费者以约 2200/秒的速度异步追平积压，最终数据库行数与消费计数精确一致（105714=105714），零丢失零重复 |

## 为什么这样做

**为什么混沌实验要真的停容器，不用代码模拟异常**：模拟异常只能验证"代码里写的 catch 逻辑本身对不对"，真的断开连接才能测出"这个依赖在真实网络故障下的行为符合我们的假设吗"——问题1和问题2都是这次真实断连才暴露出来的，如果只是在测试里手动 `throw new RuntimeException()`，很可能只测到了预期内的分支，测不到"限流拦截器完全没做异常处理"这种代码里原本就缺失的一环。

**为什么发现问题要立刻修，而不是只记录在文档里留到以后**：混沌工程的价值链条是"注入故障 → 观察真实表现 → 修复暴露出的薄弱点 → 重新验证"，只做前两步只是"知道系统脆弱在哪"，没有完成"让系统更结实"这个目的。尤其问题2这种会导致数据错误的，属于必须马上处理的级别，不能留着当已知缺陷。
