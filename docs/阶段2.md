# 阶段2：Kafka 异步削峰

## 目标

把评分写入从"客户端等数据库落库"改成"客户端只等消息进队列"，用真实压测证明这能扛住数据库连接数有限时的突发写入流量——这是"削峰填谷"要解决的具体问题，不是接个 Kafka 就算完成。

## 做了什么

**写路径改造**：`POST /api/ratings` 不再直接插库，改成校验通过后把 `RatingSubmittedEvent`（productId/userId/score）发到 Kafka topic `rating-events`（4 个分区），立即返回 `202 Accepted`。真正的插库和缓存失效交给 `RatingEventConsumer`（`@KafkaListener`）异步完成。

**分区键选 productId**：保证同一个商品的评分事件固定落到同一分区，消费顺序和该商品的历史评分顺序一致。当前实现每条事件独立插入互不影响最终聚合值，严格来说顺序不是正确性必需的，但为以后如果换成"增量更新聚合值"而不是"整体失效重算"的实现方式留了余地。

**消费者职责**：从 Kafka 取出事件 → 调用阶段1 的分表路由逻辑插入对应物理表 → 调用阶段1 的 `ScoreQueryService.evict` 失效该商品的 L1/L2 缓存，跟同步写路径的落库逻辑完全复用，只是触发时机从"HTTP 请求内同步执行"变成"消费者线程异步执行"。

**Kafka 部署**：用官方 `apache/kafka:3.7.0` 镜像的 KRaft 单节点模式，不需要额外起 Zookeeper 容器。

## 为什么这样做

**为什么不是"先插库再顺便发个消息"，而是完全把插库挪到消费者里**：如果 HTTP 请求线程里还要等 DB 插入完成，数据库连接池依然是压垮系统的瓶颈，Kafka 只是多了一次写消息的开销，没有真正起到削峰作用。只有让 HTTP 响应完全不依赖数据库操作完成，才能把"数据库处理速度"和"用户能感知到的响应延迟"彻底解耦——这才是削峰填谷的核心。

**响应从返回完整实体改成 `202 Accepted` + 回显请求内容**：数据库插入是异步的，请求处理完成的那一刻还没有生成 `id`、`createdAt`，没法诚实地返回一个"已保存"的实体。`202 Accepted` 是 HTTP 语义里"已接受，将会处理"的标准状态码，比硬凑一个假的响应体更准确地表达了系统的真实行为——调用方需要知道这是异步的，不能假设返回即落库。

**校验仍然同步执行**：`@Valid` 参数校验（比如 score 必须在 1-5）留在请求线程里同步做完才发消息，不合法的请求应该立刻拒绝，不该占用 Kafka 和消费者的处理成本，也不该让调用方等到异步消费失败才发现自己传错了参数。

## 验证方式

**基本正确性（含异步的最终一致性窗口）**：

```
POST 评分 → 202 Accepted（立即返回，此时还没有落库）
GET 立即查询 → avgScore=0, ratingCount=0（消费者还没处理，源=DB说明查库时缓存本来就没有旧值）
sleep 2s
GET 再查询 → avgScore=5.0, ratingCount=1（消费者已处理完，缓存也被消费者主动失效过一次，不是命中了过期前的旧值）
```

第二次 GET 结果也证明了消费者调用的 `evict` 生效了——如果没有这次主动失效，第一次 GET 缓存下的"0/0"会在 L1 缓存 5 秒内被命中返回错误的旧值。

**削峰效果对比（同步写库 vs 异步Kafka）**：同样用 `git worktree` 把阶段1（同步写库）代码单独跑一份在 8082 端口，阶段2（Kafka异步）代码跑在 8081，**两边都把数据库连接池上限调到 3**（`spring.datasource.hikari.maximum-pool-size=3`，只在压测时通过环境变量临时设置，没有改动仓库里的默认配置）——模拟数据库容量有限、写入压力超过其承载能力的真实场景，这正是削峰要解决的问题。用 `ab -n 1000 -c 100` 对同一个 `POST /api/ratings` 打并发突发流量：

| | QPS | P50 | P90 | P99 |
|---|---|---|---|---|
| 阶段1（同步写库，连接池瓶颈） | 1249 | 75ms | 95ms | 135ms |
| 阶段2（Kafka异步削峰） | 2727 | 15ms | 42ms | 73ms |
| 提升 | **2.2x** | **80%↓** | **56%↓** | **46%↓** |

这里有个踩坑记录：`ab` 默认把"响应体长度不一致"也计入 `Failed requests`，阶段1 的响应体里带着自增 `id` 字段，位数不同导致响应体字节数有差异，会被 `ab` 误判出几十上百个"失败请求"；用一段并发 curl 循环单独确认了所有请求实际都是 HTTP 200，不是真的失败，只是 `ab` 对变长 JSON 响应体的一个已知统计口径问题。阶段2 的响应体是固定回显请求内容，天然不会触发这个误判，这也是为什么最终对比表格里没有放"失败率"这一列——放上去会不公平地夸大差距。

**数据不丢失（最终一致性）**：本轮压测给同一个商品发了 1000 条 Kafka 事件，应用日志里 `CONSUMED productId=9001` 精确出现了 1000 次，聚合查询结果也确实体现了全部落库的数据——证明突发流量被 Kafka 缓冲后，消费者虽然处理得比同步插库慢，但最终一条不丢地全部处理完了。
