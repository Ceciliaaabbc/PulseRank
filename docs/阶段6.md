# 阶段6：Linux/TCP 内核调优 + 可观测性

## 目标

补上两块之前没做的东西：一是把服务的运行状态变成可以实时看到的监控面板，而不是只能翻日志；二是按 JD 里"熟悉 Linux 内核参数调优及 TCP/IP 协议栈优化"这条要求，在真实 Linux 内核（不是开发机的 macOS）上做连接层的参数调优实验。这个应用本地一直是用 `java -jar` 直接跑在宿主机（macOS）上的，要做 Linux 内核调优必须先把它容器化，这也是这一阶段顺带完成的事。

## 做了什么

**可观测性**：接入 Spring Boot Actuator + Micrometer，暴露 `/actuator/prometheus`。除了自动采集的 HTTP 请求量/延迟分位数、JVM 内存、GC 暂停这些通用指标，还手写了三个跟这个项目稳定性机制强相关的业务指标：
- `pulserank_score_source_total{source=...}`：按 `L1/L2/DB/DB-fallback/DEGRADED` 分类计数，能直接看出多级缓存的实际命中率
- `pulserank_ratelimit_rejected_total`：限流拒绝速率
- `pulserank_circuitbreaker_state`：熔断器当前状态(0=CLOSED/1=OPEN/2=HALF_OPEN)，Grafana 上画成时间线能直接看到跳闸和恢复的时刻

`docker-compose.yml` 里加了 Prometheus + Grafana，Grafana 用 provisioning 配置自动装好了数据源和一个 7 个面板的仪表盘（HTTP 请求速率、`/score` 延迟分位数、缓存命中来源分布、限流拒绝速率、熔断器状态、JVM 堆内存、GC 暂停时间），不需要手动点鼠标配置。

**容器化**：写了 `Dockerfile`（Maven 多阶段构建 + `eclipse-temurin:21-jre` 运行），把应用打成镜像，为下面的内核调优实验提供一个真实 Linux 环境。

**Linux 内核参数调优实验**：在这个 Linux 容器里，针对两类内核/运行时参数分别做了真实的故障复现和调优验证。

## 内核调优实验1：文件描述符上限（有清晰的 before/after，是本阶段最干净的一组数据）

把容器的 `--ulimit nofile` 故意设成 100，应用启动直接崩溃，报错定位精确：

```
java.net.SocketException: Too many open files
  at ... NioSocketChannel.newChannel
  at ... Redisson ConnectionsHolder.createConnection
```

根因是 Redisson 启动时要建立自己的连接池（默认几十个连接），加上 JVM 自身启动阶段占用的文件描述符（类加载、日志文件等），轻松超过 100 这个上限。把 `--ulimit nofile` 调到 1024，同样的镜像、同样的配置，应用正常启动、健康检查通过。这条踩坑记录直接对应生产环境一个常见的真实事故模式——本地开发机 `ulimit -n` 默认值往往够用，但打包进容器或者部署到某些默认配置很保守的环境时，这个上限不够用会在启动阶段直接崩溃，报错信息又不总是一眼能看出是内核参数问题。

## 内核调优实验2：连接队列（somaxconn / accept-count）——诚实的"没有复现预期问题"记录

**原计划**：把 `net.core.somaxconn` 和 Tomcat 的 `accept-count` 故意调小（比如5），高并发打一批新建连接（不用 keep-alive），观察连接被拒绝/重置的现象，再调大参数看问题消失，量化改善幅度。

**实际做下来没有复现出"连接被拒绝"这个现象**，做了三轮递进的实验，每轮都排除了一个可能干扰结论的因素：
1. 第一轮通过 Docker 的端口映射（`-p 8083:8081`）从宿主机打流量，`c=300` 到 `c=1000` 全部 200，没有失败——怀疑是 Docker Desktop 的端口转发（NAT/用户态代理）本身起到了缓冲作用，掩盖了容器内部真实的连接队列行为
2. 第二轮用 `--network container:<目标容器>` 让压测容器和目标容器共享同一个网络命名空间，绕开端口转发直接命中容器内部端口——同样 `c=1000`、`somaxconn=5` 依然 0 失败
3. 第三轮怀疑是请求处理太快、连接被消化的速度快于队列填满的速度，于是把 Tomcat 的工作线程数也故意调到 2（`server.tomcat.threads.max=2`），让 accept 之后的处理环节也变慢——3000 个请求、300 并发下，请求延迟从几毫秒被拖到中位数 69ms、最大 106ms（工作线程只有2个，明显在排队），但**依然没有一个连接失败**

**为什么会这样，这是一个值得记录的真实结论**：Linux 内核处理 accept 队列溢出的默认行为不是直接拒绝连接——`net.ipv4.tcp_abort_on_overflow` 默认是 0，意味着队列满了的时候内核不发 RST，而是静默丢弃新连接的 SYN-ACK，让客户端的 TCP 协议栈自己重试；只要客户端愿意重试、重试间隔内队列有空位，这个连接最终还是能建上，代价是**多花一点建连接的时间，而不是彻底失败**。要真正复现"连接被拒绝"，需要把 `tcp_abort_on_overflow` 显式调成 1（队列满了直接发 RST），或者构造一个远比这次测试更极端、持续时间更长的连接建立速率（这次是零点几秒内的瞬时脉冲，没能让积压撑到内核缓冲区都用完的程度）。

**没有为了製造一个好看的"调优前后对比"数字去做不真实的事**：可以简单地把 `tcp_abort_on_overflow` 设成 1 再测一次来"制造"出失败案例，但那样测出来的是"我改了一个和最初想验证的参数无关的开关"，不是"小 backlog 导致连接失败、调大 backlog 解决了"这个原本要验证的命题。如实记录"用三种方式都没能复现"和背后的内核行为原理，比硬凑一组数字更值得写进这份文档。

## 调优笔记（没有条件跑出戏剧性对比数据，但记录下来供参考）

这几个参数这次没有做出戏剧性的 before/after，但都是真实生产环境会用到的调优点，记录下来：
- `net.core.somaxconn` / `server.tomcat.accept-count`：仍然建议按预期并发量调大（比如 1024），即便这次实验没测出"拒绝连接"，调大它确实能让更多连接进入等待队列而不是被静默丢弃重试——在真正的高并发场景（这次没能复现的持续性、远超处理能力的连接建立速率）下依然是有意义的防线。
- `net.ipv4.tcp_tw_reuse`：允许处于 `TIME_WAIT` 状态的本地端口被新连接复用，短连接吞吐量大的服务（比如这次实验里 `ab` 不带 `-k` 的场景）容易在源端口耗尽上吃亏，这个参数能缓解，本次实验因为端口耗尽的量级没到（几千个请求远不到 `ip_local_port_range` 默认的六万多的量级）没能实测出差异。
- 文件描述符上限：见上面实验1，这条有真实复现的数据。

## 可观测性验证

启动完整技术栈后，端到端验证了整条链路：应用暴露 `/actuator/prometheus` → Prometheus 成功抓取（`up`）→ 通过 Prometheus 直接查询和通过 Grafana 数据源代理查询都能拿到正确的业务指标数值 → Grafana 仪表盘 7 个面板全部加载成功。产生一批读请求后，`pulserank_score_source_total{source="L1"}` 和 `{source="DB"}` 的计数精确对应实际的缓存命中/未命中次数，指标不是摆设。

## 为什么这样做

**为什么要专门写一个 Dockerfile，而不是直接在宿主机上改 macOS 的内核参数**：这个项目从阶段0开始应用就是直接跑在开发者的 macOS 上，JD 要求的是 Linux 内核参数调优——macOS 和 Linux 的网络栈参数体系完全不是一回事（macOS 用 `sysctl -w kern.ipc.somaxconn` 这类完全不同的命名空间），要做真正对口的 Linux 内核调优，必须让应用跑在一个真实的 Linux 环境里，Docker Desktop 的 Linux 虚拟机刚好提供了这个环境。

**为什么发现"没有复现预期问题"之后没有继续加码去凑一个数字**：这份文档从阶段0开始就一直遵循"数据说话"的原则——阶段4 发现 GC 不是瓶颈时如实报告了，这里发现内核的连接队列处理机制比想象中更宽容，也应该如实报告。诚实地记录"做了什么严谨的排除法实验、得到了什么真实结论、背后的原理是什么"，比包装一个不真实的性能提升数字更有价值，也更能体现对这个领域机制的实际理解程度。
