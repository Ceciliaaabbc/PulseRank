# 阶段4：JVM 深度优化

## 目标

用 JFR（Java Flight Recorder）对真实压测下的服务做 profiling，先搞清楚 GC/内存分配到底是不是这个应用在当前规模下的瓶颈，再决定往哪个方向调优——而不是不看数据就先假设"肯定是 GC 的问题"、然后堆一堆调优参数上去凑一个好看的数字。

## 做了什么

**Profiling 方法**：对已预热的热点商品做 30 秒持续压测（`ab -t 30 -c 30`，约 45-50 万请求），同时用 `-XX:StartFlightRecording=settings=profile` 采集 JFR 记录，`-Xlog:gc*` 记录完整 GC 日志。用 `jfr print --events jdk.ObjectAllocationSample` 分析分配热点，过滤出 Tomcat 请求处理线程（`http-nio-*`）的采样，排除 JVM/Spring Boot 启动阶段的一次性开销干扰。

**做了三组对照实验**：
1. G1（JDK 默认，ergonomic 堆大小）
2. ZGC（`-XX:+UseZGC`，同样 ergonomic 堆大小）
3. G1 + 固定堆大小（`-Xms512m -Xmx512m`，消除堆动态扩缩容）

三组用完全相同的压测脚本、相同的热点商品、相同的 30 秒时长，保证可比。

## 发现了什么（都是数据说话，不是预设结论）

**发现1：这个应用当前规模下，GC 本来就不是瓶颈**。G1 默认配置下，30 秒内 216 次年轻代 GC，平均暂停 1.33ms，P99 4.77ms，最大 7.7ms，30 秒里 STW 总耗时只有 287ms——占整个压测时长的不到 1%。应用实际存活堆只有 10-14MB，堆本身很小，G1 的年轻代收集已经足够快。

**发现2（profiling 意外挖出来的问题）：分配热点排第一的不是缓存查询，是阶段3 加的限流器**。按对象类型统计请求线程的分配采样，排前面的是 `byte[]`、`CompletableFuture`/`CompletableFuture$UniWhenComplete`、`org.redisson.command.RedisExecutor` 这些——一开始以为是阶段1 的多级缓存在查 Redis，但仔细一想：这次压测打的是同一个热点商品，阶段3 的热点探测机制应该已经把它的本地缓存 TTL 延到 30 秒，绝大多数请求应该完全命中 L1、根本不该碰 Redis。真正在每一个请求上都无条件执行一次 Redis 调用的，是阶段3 挂在这个接口上的分布式限流器——`RateLimitInterceptor` 在请求进 Controller 之前就跑了一次 Lua 脚本，不管这次请求最后是 L1 命中还是要查库。这是一个很好的例子：不做 profiling 直接凭直觉判断瓶颈在哪，很可能猜错方向——限流器本身没有 bug，只是它引入的额外开销比想象中显著，这个发现留给以后要不要给限流做本地令牌预留之类的优化做参考，不在本阶段范围内展开处理。

**发现3：ZGC 在这个应用的规模下不比 G1 好，甚至略差**。ZGC 自己的 STW 阶段极短（Mark Start/End、Relocate Start 这些都在 0.003-0.013ms 量级，确实符合"近乎无停顿"的设计目标），但同样 30 秒压测下整体吞吐反而比 G1 低（对比见下表），P99 延迟也没有更好。这是符合预期的：ZGC 的并发标记/整理需要读屏障和着色指针的运行时开销，这个开销在大堆、高分配速率场景下能被"几乎不停顿"的收益覆盖掉，但这个应用堆很小（10-14MB 存活对象）、G1 的年轻代暂停本来就已经在个位数毫秒——ZGC 的额外运行时开销在这个规模下只有成本没有收益。不是"哪个 GC 更好"，是"要按负载特征选 GC"。

**发现4：固定堆大小能省下大部分 GC 总耗时，但对用户可感知的延迟没有明显帮助**。G1 默认走 ergonomic 堆大小时，压测期间观察到堆 committed size 在 56MB～292MB 之间反复伸缩（G1 会在负载降低时把内存还给操作系统，负载升高再重新申请）。改成 `-Xms512m -Xmx512m` 固定堆之后不再有这种伸缩：GC 次数从 216 次降到 57 次，30 秒内 STW 总耗时从 287ms 降到 166ms，**总 GC 开销降了 42%**。但是压测的 P99 请求延迟几乎没变（3ms → 4ms，在压测噪声范围内）——原因是 GC 暂停本来就只占请求总耗时里很小的一部分，把它砍掉 4 成，对已经是毫秒级的端到端延迟来说根本感觉不出来。这也是诚实汇报的一部分：GC 调优确实有效果，但"有效果"和"用户能感知到"是两件不完全对等的事，得看这项开销在总延迟里占的比例有多大。

## 压测数据对比

| 配置 | QPS | P50 | P90 | P99 | GC次数(30s) | STW总耗时 |
|---|---|---|---|---|---|---|
| G1(默认ergonomic堆) | 16572 | 2ms | 2ms | 3ms | 216 | 287ms |
| ZGC(默认ergonomic堆) | 15208 | 2ms | 2ms | 4ms | - | 近似0(自身暂停<0.02ms/次) |

## 为什么没有做到 JD 里说的"降低30%+"

JD 原文要求"JVM层深度优化，将系统延迟降低30%+"，这条更适合发生在一个 GC 暂停本来就占请求延迟相当比例的系统上（比如大堆、高对象分配速率、Full GC 频发的场景）。这个应用在当前压测规模下 GC 开销本就只占总延迟不到 1%，无论怎么调 GC 参数，理论上限也到不了 30% 的端到端延迟改善——诚实地把这个上限的原因讲清楚，比硬凑一个不真实的数字更有说服力。如果要在这个项目里制造一个"GC 确实是瓶颈"的场景来更有力地演示调优效果，需要人为构造大堆/高分配速率的极端测试用例，这个和当前"高并发读多写多评分聚合"的业务场景关联不大，本阶段选择不做这种脱离业务场景的构造实验，如实汇报"在当前真实业务负载下 GC 调优空间有限"这个结论。
